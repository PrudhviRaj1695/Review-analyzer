# Alembic Migrations Explained

## What is Alembic?

Alembic is a database migration tool for SQLAlchemy. Instead of manually creating tables with `Base.metadata.create_all()`, Alembic:
- **Tracks schema changes** in version-controlled Python files
- **Auto-generates migrations** from ORM model changes
- **Upgrades/downgrades** databases safely
- **Maintains migration history** (reproducible deployments)

### Before Alembic (Manual):
```python
# App startup

Base.metadata.create_all(bind=engine)  # Creates ALL tables at once
# ❌ No history, no way to undo, no migration control
```

### With Alembic (Versioned):
```bash
alembic revision --autogenerate -m "add users table"  # Generate migration
alembic upgrade head                                   # Apply it
alembic downgrade -1                                   # Undo last one
```

## The upgrade() Function

This runs when you do `alembic upgrade head`. It applies the schema changes:

```python
def upgrade() -> None:
    """Upgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.create_table('products',
    sa.Column('id', sa.Integer(), autoincrement=True, nullable=False),
    sa.Column('name', sa.String(length=255), nullable=False),
    sa.Column('price', sa.Numeric(precision=10, scale=2), nullable=False),
    sa.Column('rating', sa.Numeric(precision=3, scale=2), nullable=True),
    sa.PrimaryKeyConstraint('id')
    )
```

**What it does:**

```sql
-- What Alembic executes:
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name VARCHAR(255) NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    rating NUMERIC(3, 2)
);
```

**Mapping ORM → SQL:**

| ORM Model | SQL Generated |
|---|---|
| `Column('id', Integer(), autoincrement=True, nullable=False)` | `id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL` |
| `Column('name', String(255), nullable=False)` | `name VARCHAR(255) NOT NULL` |
| `Column('price', Numeric(10,2), nullable=False)` | `price NUMERIC(10, 2) NOT NULL` |
| `Column('rating', Numeric(3,2), nullable=True)` | `rating NUMERIC(3, 2)` |
| `PrimaryKeyConstraint('id')` | `PRIMARY KEY (id)` |

### Second Table: Reviews

```python
op.create_table('reviews',
    sa.Column('id', sa.Integer(), autoincrement=True, nullable=False),
    sa.Column('product_id', sa.Integer(), nullable=False),
    sa.Column('text', sa.Text(), nullable=False),
    sa.Column('created_at', sa.DateTime(), nullable=True),
    sa.ForeignKeyConstraint(['product_id'], ['products.id'], ),  # ← FK!
    sa.PrimaryKeyConstraint('id')
)
```

**Generated SQL:**
```sql
CREATE TABLE reviews (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    product_id INTEGER NOT NULL,
    text TEXT NOT NULL,
    created_at DATETIME,
    FOREIGN KEY (product_id) REFERENCES products(id)
);
```

**Key part: Foreign Key**
```python
sa.ForeignKeyConstraint(['product_id'], ['products.id'], )
```

This ensures:
- Every review must have a valid `product_id`
- Can't insert review with `product_id` that doesn't exist
- Prevents orphan reviews

## The downgrade() Function

This runs when you do `alembic downgrade -1`. It **reverses** the upgrade:

```python
def downgrade() -> None:
    """Downgrade schema."""
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_table('reviews')     # Drop in reverse order (FK dependency first)
    op.drop_table('products')
    # ### end Alembic commands ###
```

**What it does:**
```sql
DROP TABLE reviews;    -- FK references products, must drop first!
DROP TABLE products;   -- Then drop the referenced table
```

**Important: Order matters!**
- `upgrade()`: Create `products` first, then `reviews` (FK dependency)
- `downgrade()`: Drop `reviews` first, then `products` (reverse order)

If you did it wrong (drop products first), you'd get FK constraint error.

## How Alembic Autogenerated This

When you ran:
```bash
alembic revision --autogenerate -m "initial"
```

Alembic did this:

```
1. Read DATABASE_URL from environment
   ↓
2. Connect to database
   ↓
3. Query current schema (tables, columns, constraints)
   DATABASE: (empty - no tables)
   ↓
4. Read ORM models from app/models.py
   ORM: products table, reviews table (with FK)
   ↓
5. Compare: ORM models vs database schema
   Difference: ORM has tables but DB doesn't
   ↓
6. Generate migration script
   "Create products table"
   "Create reviews table"
   ↓
7. Write to alembic/versions/520463b5e478_initial.py
```

## Migration Commands Reference

### Generate a new migration
```bash
# Autogenerate from ORM model changes
alembic revision --autogenerate -m "add username to users"

# Or write manually (for custom SQL)
alembic revision -m "create custom index"
```

### Apply migrations
```bash
# Apply all pending migrations
alembic upgrade head

# Apply next 1 migration
alembic upgrade +1

# Apply to specific revision
alembic upgrade 520463b5e478
```

### Undo migrations
```bash
# Undo last migration
alembic downgrade -1

# Undo all migrations
alembic downgrade base
```

### Check migration status
```bash
# Show current revision
alembic current

# Show migration history
alembic history

# Show heads (latest revisions)
alembic heads
```

## Migration Flow: Real Example

### Scenario: Add `description` column to products

**Step 1: Modify ORM model**
```python
# app/models.py
class Product(Base):
    __tablename__ = "products"
    id = Column(Integer, primary_key=True)
    name = Column(String(255), nullable=False)
    price = Column(Numeric(10, 2), nullable=False)
    rating = Column(Numeric(3, 2))
    description = Column(String(500))  # ← NEW
```

**Step 2: Generate migration**
```bash
alembic revision --autogenerate -m "add description to products"
```

**Generated script will contain:**
```python
def upgrade():
    op.add_column('products', sa.Column('description', sa.String(length=500)))

def downgrade():
    op.drop_column('products', 'description')
```

**Step 3: Apply migration**
```bash
alembic upgrade head
```

**What SQL runs:**
```sql
ALTER TABLE products ADD COLUMN description VARCHAR(500);
```

**Step 4: Undo if needed**
```bash
alembic downgrade -1
```

**What SQL runs:**
```sql
ALTER TABLE products DROP COLUMN description;
```

## Key Advantages

| Feature | Manual (`create_all()`) | Alembic (Migrations) |
|---|---|---|
| **Version control** | ❌ No history | ✅ Each change tracked |
| **Reproducibility** | ❌ Can't recreate in stages | ✅ Replay any migration |
| **Undo/rollback** | ❌ Must drop/recreate manually | ✅ `downgrade -1` |
| **Team collaboration** | ❌ Merge conflicts in Python | ✅ Separate migration files |
| **Deployment safety** | ❌ All-or-nothing | ✅ Apply one at a time |
| **Zero-downtime deploys** | ❌ Risky | ✅ Plan migrations carefully |
| **Documentation** | ❌ Lost | ✅ Each migration documents change |

## How We Use It in This Project

**Before (init_db.py):**
```python
def init_db():
    Base.metadata.create_all(bind=engine)  # Creates all at once
```

**After (Alembic):**
```bash
# At app startup, Alembic ensures database is up-to-date
alembic upgrade head

# When you change models:
alembic revision --autogenerate -m "description"
# Commit the new migration file
# Deploy and run: alembic upgrade head
```

**In production:**
- Database migrations are code-reviewed
- Each change is tracked
- Can rollback any version
- Team knows what changed and when

## Next Steps

To upgrade to PostgreSQL:

1. **Update .env:**
   ```
   DATABASE_URL=postgresql://user:password@localhost/db
   ```

2. **Run migrations:**
   ```bash
   alembic upgrade head
   ```

Alembic will run the SAME migration scripts against PostgreSQL. The SQL generated is database-agnostic.
