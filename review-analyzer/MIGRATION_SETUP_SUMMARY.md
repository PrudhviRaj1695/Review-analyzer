## The Generated Migration: `520463b5e478_initial.py`

This migration creates the initial schema:

### upgrade() Function
```python
def upgrade() -> None:
    """Upgrade schema - creates tables."""
    # Creates products table
    op.create_table('products',
        sa.Column('id', sa.Integer(), autoincrement=True, nullable=False),
        sa.Column('name', sa.String(length=255), nullable=False),
        sa.Column('price', sa.Numeric(precision=10, scale=2), nullable=False),
        sa.Column('rating', sa.Numeric(precision=3, scale=2), nullable=True),
        sa.PrimaryKeyConstraint('id')
    )
    
    # Creates reviews table
    op.create_table('reviews',
        sa.Column('id', sa.Integer(), autoincrement=True, nullable=False),
        sa.Column('product_id', sa.Integer(), nullable=False),
        sa.Column('text', sa.Text(), nullable=False),
        sa.Column('created_at', sa.DateTime(), nullable=True),
        sa.ForeignKeyConstraint(['product_id'], ['products.id']),  # ← FK ensures integrity
        sa.PrimaryKeyConstraint('id')
    )
```

**What it does:**
- Creates `products` table with 4 columns (id, name, price, rating)
- Creates `reviews` table with 4 columns (id, product_id, text, created_at)
- Adds FK constraint: `product_id` must reference existing `products.id`
- Sets up autoincrement primary keys

**Generated SQL (SQLite):**
```sql
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name VARCHAR(255) NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    rating NUMERIC(3, 2)
);

CREATE TABLE reviews (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    product_id INTEGER NOT NULL,
    text TEXT NOT NULL,
    created_at DATETIME,
    FOREIGN KEY (product_id) REFERENCES products(id)
);
```

### downgrade() Function
```python
def downgrade() -> None:
    """Downgrade schema - drops tables."""
    op.drop_table('reviews')   # Drop FK dependent table first
    op.drop_table('products')  # Then drop referenced table
```

**Why this order matters:**
- Can't drop `products` if `reviews` has FK references to it
- Downgrade must reverse the upgrade in opposite order

## Key Architecture Change

### Before (Manual)
```python
# app/init_db.py
def init_db():
    Base.metadata.create_all(bind=engine)  # Creates all tables at once
    
# app/main.py - app startup
init_db()  # Called on startup
```

**Problems:**
- ❌ No version control of schema changes
- ❌ Can't undo changes
- ❌ Can't track who changed what
- ❌ Risky for teams

### After (Alembic)
```bash
# Generate migration when you change models
alembic revision --autogenerate -m "description"

# Apply when deploying
alembic upgrade head

# Undo if needed
alembic downgrade -1
```

**Benefits:**
- ✅ Migrations are version-controlled Python files
- ✅ Can undo any change
- ✅ Full audit trail of schema changes
- ✅ Team coordination is seamless
- ✅ Production deployments are reproducible

## How to Use Going Forward

### When You Change ORM Models

```python
# Example: Add new column to Product
class Product(Base):
    __tablename__ = "products"
    id = Column(Integer, primary_key=True)
    name = Column(String(255))
    price = Column(Numeric(10, 2))
    description = Column(String(500))  # ← NEW
```

### Generate Migration
```bash
alembic revision --autogenerate -m "add description to products"
# Creates: alembic/versions/abc123def456_add_description_to_products.py
```

### Review Generated Migration
```python
# alembic/versions/abc123def456_add_description_to_products.py
def upgrade():
    op.add_column('products', sa.Column('description', sa.String(length=500)))

def downgrade():
    op.drop_column('products', 'description')
```

### Apply Migration
```bash
alembic upgrade head
# Runs: ALTER TABLE products ADD COLUMN description VARCHAR(500);
```

### Commit to Git
```bash
git add alembic/versions/abc123def456_add_description_to_products.py
git commit -m "Add description column to products"
```

alembic downgrade -1

alembic current

alembic history

alembic downgrade base
